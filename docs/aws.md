## 개요

### Problem · Evidence

예약 서비스는 장애 상황에서도 계속 쓸 수 있어야 합니다. **예약이 안 되는 순간이 곧 이탈**입니다. 그런데 안정성을 높이려고 인프라를 무조건 확장하면 그게 그대로 **고정비**가 됩니다.

초기 산정 **월 약 27만 원**. 서비스 규모에 비해 과한 구성이었고, **초과 스펙은 줄이는 결정을 아무도 하지 않습니다.**

| 구성 대안 | 얻는 것 | 치르는 것 | 판단 |
|---|---|---|---|
| A. 단일 리전 + 백업 | 가장 저렴 | 리전 장애 시 서비스 전체 정지 | 기각 |
| B. 멀티 리전 Active-Active | 전환 시간 거의 0 | 두 리전 상시 구동 → **고정비 두 배** | 기각 |
| C. 멀티 리전 3-Tier (Active-Standby) | 리전 장애 대응 범위 확보 | 전환 시간 · 복제 지연 | **채택** |

### 나의 활동 — 팀장으로 무엇을 했나

4인 팀의 **팀장**이었고 기여도는 60%입니다. 맡은 범위는 **요구사항·운영 조건 정의 · 비용과 안정성 기준 의사결정 · AWS 아키텍처 설계 · ECS 구성 · 운영 환경 구축**입니다.

가장 먼저 한 일은 코드를 짜는 게 아니라 **기준을 문서로 정하는 것**이었습니다. “허용 가능한 다운타임은 어디까지인가”, “월 예산 상한은 얼마인가” 두 가지를 팀 합의로 먼저 못 박았습니다.

**기준이 없으면 모든 확장이 정당해 보입니다.** 안정성은 사고 싶은 만큼 살 수 있는 것이라 상한선이 없으면 끝없이 커집니다. 그래서 “안정성을 얼마나 살 것인가”를 **기술 선택이 아니라 기준 설정 문제**로 놓고 시작했습니다.

이후 모든 구성 선택은 그 기준으로 판정했습니다 — Active-Active를 기각한 것도, NAT Gateway 개수를 다시 본 것도 같은 잣대였습니다.

### 핵심 성과 · Key Achievements

- **인프라 비용 구조 분해** 산정표를 항목별로 뜯어 **NAT Gateway가 단일 최대 항목(월 약 $160)**임을 찾아내고, “트래픽이 없어도 나가는 고정비”부터 재산정 → 예상 월 운영비 **약 20% 절감** (초기 산정 27만 원 기준)

- **리전 장애 대응** 멀티 리전 **3-Tier Active-Standby** 구성으로 단일 리전 장애 시 서비스 지속. Active-Active는 **고정비 두 배**라는 이유로 명시적으로 기각

- **서비스 디스커버리** 오토스케일링으로 컨테이너 IP가 바뀔 때마다 끊기던 라우팅을 **ECS Service Connect**로 전환 — IP 고정이 아니라 **이름으로 찾는 구조**로 바꿔 수동 갱신 제거

- **분산 로그 중앙화** **Fluent Bit 사이드카 → OpenSearch → Kibana + Slack 알림**으로 “어느 컨테이너에서 터졌는지 모르는” 상태를 해소, 디버깅 시간 단축

## 기술 의사결정

### Technical Decision

| 결정한 것 | 고른 것 | 기각한 것 | 사유 · 감수한 것 |
|---|---|---|---|
| 장애 대응 범위 | **멀티 리전 3-Tier** (Active-Standby) | ① 단일 리전 + 백업 ② Active-Active | ①은 리전 장애 = 전체 정지. ②는 고정비 두 배로 27만 원 기준에서 불가. *감수*: 전환 시간. |
| 리전 간 데이터 | **비동기 복제** | 실시간 동기 복제 | 동기 복제는 쓰기 지연이 두 리전 왕복에 묶입니다. **평상시 응답 속도를 희생하면서 장애 대비를 사는 건 순서가 틀렸다**고 봤습니다. *감수*: 복제 지연 구간의 정합성. |
| 규모 산정 방식 | **예상 사용량에서 리소스별 용량 역산** | 여유 있게 잡고 나중에 축소 | 초과 스펙은 줄이는 결정을 아무도 하지 않습니다. **결과: 약 20% 절감** (초기 산정 27만 원 대비). |
| 실행 환경 | **ECS + Docker** | EC2 직접 관리 / EKS | 서버 관리 인력이 없습니다. 실행 환경 표준화가 먼저입니다. *감수*: 세밀한 튜닝 여지가 줄어듭니다. |

트래픽이 예측 불가였다면 규모 산정을 고정 용량이 아니라 오토스케일링 기반으로 갔을 것입니다.

### Infra 의사결정 — 왜 이 구성인가

Q. 비용을 어디서 줄였나 — “20% 절감”의 실체

산정표를 다시 열어보면 비용 구조가 한쪽으로 심하게 쏠려 있었습니다. **NAT Gateway가 단일 최대 항목**입니다.

| 항목 | 월 비용(산정표 기준) | 비중 |
|---|---|---|
| **NAT Gateway 계열** (버지니아 $120 + 서울 $40) | **약 $160** | **가장 큼** |
| ALB | 약 $48 |  |
| EC2 (버지니아 $28 + 서울 $19) | 약 $47 |  |
| CloudFront · VPC Peering 등 | 소액 |  |

처음 구성이 **리전당 NAT Gateway 2개**였습니다. AZ 이중화를 위해 관행대로 둘씩 둔 것인데, NAT는 **시간당 요금 + 데이터 처리 요금**이 둘 다 붙어서 트래픽이 거의 없는 단계에서도 고정비가 그대로 나갑니다.

**“안 쓰는데도 나가는 돈”부터 잘라야 한다**는 기준을 세우고, 여기와 과대 산정된 인스턴스 스펙을 다시 계산했습니다. 이게 **약 20% 절감**의 실제 내용입니다.

**성과**예상 월 운영비 **약 20% 절감** — 27만 원 산정 기준. 줄인 몫의 대부분이 NAT Gateway에서 나왔습니다.

**감수한 것** Standby 리전의 AZ 이중화 수준이 낮아집니다. Active 리전이 통째로 죽는 시나리오는 커버하지만, Standby 안에서 AZ 하나가 죽는 경우까지는 감당 범위를 줄였습니다. **돈을 내고 사는 안정성에는 우선순위가 있다**고 봤습니다.

Q. 왜 ECS + Fargate인가 — EC2 직접 관리와 EKS를 두고

MSA로 쪼갠 서비스를 각각 배포해야 했습니다. 선택 기준은 단 하나, **“운영할 사람이 없다”** 였습니다.

| 선택지 | 얻는 것 | 치르는 것 | 판정 |
|---|---|---|---|
| EC2에 직접 배포 | 가장 저렴하고 통제력이 큼 | OS 패치 · 스케일 · 헬스체크를 전부 우리가. 4인 팀에 전담 인력 없음 | 기각 |
| EKS (Kubernetes) | 표준 오케스트레이션, 이식성 | 컨트롤 플레인 고정비 + **학습·운영 비용**. 프로젝트 기간을 넘김 | 기각 |
| **ECS + Fargate** | 서버 자체를 관리 대상에서 제거. 태스크 정의만 쓰면 됨 | 세밀한 튜닝 여지가 줄고 AWS 락인이 깊어짐 | **채택** |

**성과**서버 인스턴스를 **관리 대상에서 제거**. 4인 팀에 인프라 전담 없이도 배포가 돌아갔습니다.

**감수한 것** AWS 종속입니다. 다른 클라우드로 옮기려면 태스크 정의부터 다시 씁니다. 기간과 인력이 제약인 프로젝트에서 **이식성은 지금 사지 않아도 되는 보험**이라고 판단했습니다.

Q. 컨테이너 IP가 계속 바뀌는 문제 — 왜 Service Connect인가

오토스케일링으로 태스크가 재생성될 때마다 IP가 바뀌었고, API Gateway가 뒷단으로 라우팅할 때마다 **네트워크 설정을 수동으로 갱신**해야 했습니다.

| 선택지 | 얻는 것 | 치르는 것 | 판정 |
|---|---|---|---|
| IP를 고정한다 | 당장 문제가 사라짐 | **오토스케일링을 포기**하는 것과 같음. 원인이 아니라 증상을 막는 것 | 기각 |
| 서비스마다 내부 ALB | 주소가 안정적 | 서비스 수만큼 로드밸런서 비용. NAT에 이어 또 고정비 | 기각 |
| **ECS Service Connect** | 프록시 기반 DNS 서비스 디스커버리 — **IP가 아니라 이름으로** 찾음. 스케일아웃 시 로드밸런싱 자동 | ECS 생태계에 더 묶임. 프록시 사이드카가 태스크마다 붙음 | **채택** |

**성과**오토스케일링 중 **수동 네트워크 갱신 0회**. 스케일아웃 시 로드밸런싱도 자동으로 따라왔습니다.

**여기서 배운 것** IP를 고정하려던 첫 시도가 방향 자체가 틀렸습니다. **“주소가 변한다”를 막을 문제로 보지 않고 전제로 받아들이자** 해법이 바뀌었습니다.

Q. Aurora와 DynamoDB를 왜 같이 쓰나 — 하나로 통일하지 않고

데이터의 성격이 달랐습니다. **예약**은 중복 예약이 생기면 안 되는 **정합성** 문제이고, **조회 · 세션**은 초당 요청이 몰리는 **속도** 문제입니다.

하나로 통일하면 둘 중 하나는 잘못된 도구를 씁니다. Aurora만 쓰면 조회 트래픽이 예약 트랜잭션을 밀어내고, DynamoDB만 쓰면 **예약의 정합성을 애플리케이션이 직접 책임져야** 합니다.

**성과**예약의 정합성과 조회의 속도를 **같은 요청 안에서 서로 다른 경로**로 처리.

**감수한 것** 저장소가 둘이라 백업 · 모니터링 · 스키마 변경이 두 벌입니다. DERO에서는 반대로 하나로 합쳤습니다 — 기준은 ‘데이터의 종류’가 아니라 **‘같이 조회되는가’**였습니다.

Q. 로그를 왜 Fluent Bit 사이드카로 모았나

MSA로 나누고 나니 **오류는 났는데 어느 컨테이너에서 났는지 알 수 없는** 상태가 됐습니다. 컨테이너별로 로그가 흩어져 시간순 재구성이 불가능했습니다.

| 선택지 | 얻는 것 | 치르는 것 | 판정 |
|---|---|---|---|
| 애플리케이션에서 직접 전송 | 추가 컨테이너 없음 | 서비스마다 로깅 코드를 심어야 함. 언어·프레임워크가 다르면 제각각 | 기각 |
| CloudWatch Logs만 | 설정이 가장 쉬움 | 검색·집계가 약해 **시간순 교차 추적**이 어려움 | 부족 |
| **Fluent Bit 사이드카 → OpenSearch** | 앱 코드를 건드리지 않고 수집. Kibana에서 교차 검색. **에러 발생 시 Slack 알림** | 태스크마다 사이드카가 붙어 리소스를 나눠 씀 | **채택** |

**성과**“어느 컨테이너에서 터졌는지 모르는” 상태 해소. 에러 발생 시 **Slack 즉시 알림**.

**가장 아쉬운 점** 이걸 **설계 단계가 아니라 문제를 겪은 뒤에** 붙였습니다. 컨테이너를 2개 이상 띄우기로 결정한 그 순간에 로그 경로를 같은 그림에 그렸어야 했습니다.

## 아키텍처

### 예약 요청 처리 흐름

***정합성은 Aurora, 속도는 DynamoDB.** ③이 트랜잭션으로 막히는 구간이고 ⑤는 막히면 안 되는 구간이라, 두 요구가 **같은 요청 안에서 서로 다른 경로**를 타게 나눴습니다.*

### Architecture · Tech Stack

![](/assets/aws-infra-arch.webp)

***서비스 수준 구성도** — 외부에 열리는 것은 Load Balancer까지. 앱과 데이터 계층은 Private 서브넷 안에 두고, 데이터 계층은 가용영역 2개에 Primary·Secondary로 나눠 한 가용영역이 죽어도 읽기가 살아있게 했습니다. CDA 최종 발표자료 p15.*

![](/assets/aws-arch-single.webp)

***단일 리전** — 열려야 하는 것(CloudFront · ALB)과 열리면 안 되는 것(DB · 앱)을 서브넷으로 물리 분리. 감수한 것은 NAT 게이트웨이 비용. 컨테이너는 재시작되므로 로그를 stdout으로 밖에 뻐다.*

![](/assets/aws-arch-multi.webp)

***멀티 리전** — 쓰기는 Primary 한 곳으로만 받고 Secondary는 읽기 전용으로 고정했다. 감수한 것 — Primary가 죽으면 쓰기가 멈춘다. 자동 전환 대신 수동 승인을 택한 것도 오탐의 비용이 더 컸기 때문.*

보안 경계를 구조로 고정했습니다.

*외부에 열리는 건 ALB까지입니다. 데이터 계층은 Private 서브넷에 두고 보안그룹으로 계층별 출입을 제한했습니다 — 열어두고 조이는 게 아니라 닫고 필요한 경로만 엽니다.*

**보안 경계를 구조로 고정했습니다.** 외부에 열리는 건 ALB까지입니다. 데이터 계층은 Private 서브넷에 두고 보안그룹으로 출입을 계층별로 제한했습니다. “열어두고 나중에 조인다”가 아니라 **처음부터 닫고 필요한 경로만 연다**는 순서로 갔습니다.

## 트러블슈팅

### Troubleshooting — 뒷단으로 가는 요청이 간헐적으로 실패했다

증상

게이트웨이에서 뒷단으로 가는 요청이 간헐적으로 실패했습니다.

처음 가설

백엔드가 죽었다고 봤습니다. **틀렸습니다** — 태스크는 살아 있었고 주소만 바뀌어 있었습니다.

실제 원인

오토스케일링으로 컨테이너가 재생성될 때마다 **IP가 변경**됐습니다.

해결

**ECS Service Connect**(프록시 기반 DNS 서비스 디스커버리) — IP를 고정하는 방향이 아니라 **이름으로 찾는 방향**으로 바꿨습니다.

### Troubleshooting — 오류는 났는데 어디서 났는지 알 수 없었다

증상

오류는 났는데 **어느 컨테이너에서 났는지** 알 수 없었습니다.

실제 원인

해결

## 회고

### Result · Retrospective

예상 월 운영 비용 **약 20% 절감**(초기 산정 27만 원 기준) · 단일 리전 장애 시 서비스 지속 · **프로젝트 경진대회 최우수상**.

잘한 점

구성을 정하기 전에 **비용과 안정성의 기준을 팀 합의로 먼저 정한 것.** 이후 모든 선택이 그 기준으로 판정됐습니다.

배운 점

관측은 기능이 아니라 **전제**입니다. 분산 환경에서 “어디서 터졌는지 모른다”는 상태 자체가 장애입니다.

아쉬운 점

용량을 **실제 부하로 재보지 않고** 예상 사용량만으로 산정했습니다.

다음에는

컨테이너를 2개 이상 띄우기로 결정한 **그 시점에 로그 경로를 같은 그림에** 그립니다. 인프라 구성 전에 허용 다운타임과 월 예산 상한을 숫자로 먼저 합의합니다.
