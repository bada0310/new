실시간 노션 퀴즈 쇼 — 스터디 운영 자동화

2026.03 – 04 · 개인 프로젝트

말로 하던 출제 · 응답 · 채점 · 집계를 실시간 웹 도구로 옮겼습니다. 회차당 준비시간 3~4시간 → 2시간.

개인기획 · 개발 · 운영
GitHub ↗

Problem · 계측

CS 스터디를 운영하면서 매 회차 3~4시간이 들었습니다. 그런데 그 시간의 대부분이 공부가 아니라 운영이었습니다 — 노션에 흩어진 정리 글에서 문제를 뽑고, 사람마다 답을 받고, 채점하고, 집계하는 일.

공부에 쓰는 시간과 운영에 쓰는 시간을 나눠서 재보니 운영 쪽이 줄일 수 있는 부분이었습니다.

핵심 성과 · Key Achievements

  • 회차 준비 3~4시간 → 2시간 공부 시간과 운영 시간을 나눠 재보고 줄일 수 있는 쪽이 운영이라는 걸 먼저 확인한 뒤 손댔습니다 (CS 스터디 기준)
  • 새 도구를 배우게 하지 않았다 전용 출제 페이지를 만들면 ‘정리 → 옮겨적기’ 단계가 늘어납니다. 대신 Notion API로 출제자 단위 child_database 블록을 탐색해, 평소처럼 정리만 하면 그게 그대로 문제가 되게 했습니다
  • 모두가 같은 순간에 같은 문제 폴링이면 사람마다 문제가 뜨는 시점이 어긋나 먼저 받은 사람이 유리해집니다. WebSocket 브로드캐스트로 바꿨습니다
성과 1건 더 보기
  • 반복 판단의 도구화 출제 · 응답 · 채점 · 집계를 사람 손에서 걷어냈습니다. “사람이 매번 같은 결정을 하고 있으면 코드로 옮길 수 있다”를 이후 프로젝트에서도 먼저 봅니다

설계 의사결정 — 새 도구를 배우게 하지 않기

Q. 왜 전용 출제 화면을 만들지 않고 Notion을 읽었나

가장 쉬운 구현은 출제용 관리자 페이지를 하나 만드는 것입니다. 그런데 스터디원들은 이미 노션에 정리하고 있었습니다.

새 도구를 만들면 정리 → 문제 옮겨적기라는 단계가 하나 늘어납니다. 줄이려던 시간을 다시 쓰는 셈입니다.

그래서 Notion API로 출제자 단위의 child_database 블록을 찾아 문제를 추출하는 쪽으로 갔습니다. 출제자는 평소처럼 정리만 하면 그게 그대로 문제가 됩니다.

선택지얻는 것치르는 것판정
전용 출제 페이지구조가 내 통제 아래. 파싱 깨질 일 없음사용자에게 새 습관을 요구. 옮겨적는 시간이 그대로 남음기각
Notion API로 읽기기존 습관을 그대로 씀. 준비시간이 실제로 줄어듦노션 표 구조가 바뀌면 추출이 깨짐. API 호출 제한에 묶임채택

결과 회차당 준비시간 3~4시간 → 2시간. 줄어든 시간은 전부 운영 쪽에서 나왔습니다. 감수한 것 남의 서비스 데이터 구조에 의존한다는 것. 실제로 표 구조가 바뀌어 추출이 깨진 적이 있습니다.

Q. 왜 WebSocket인가 — 폴링으로는 안 되나

퀴즈 쇼는 모두가 같은 순간에 같은 문제를 보고 있어야 성립합니다. 폴링이면 사람마다 문제가 뜨는 시점이 어긋나고, 먼저 받은 사람이 유리해집니다.

감수한 것 연결 상태를 직접 관리해야 합니다. 재접속 시 상태 복원이 실제로 남은 숙제이고, 아직 정리 중입니다.

How it works

Notion 페이지 → Notion API로 출제자 단위 child_database 탐색
        → 문제 추출 · 정규화
        → Uvicorn :8000
        → WebSocket 브로드캐스트 → 참가자 화면 동시 갱신
        → 제출 집계 · 채점 · 결과 표시

출제자가 평소처럼 노션에 정리만 하면 그게 그대로 문제가 됩니다. 새로운 도구를 배우게 하지 않는 것이 설계 조건이었습니다.

Result

반복되는 판단을 도구로 옮긴 첫 경험입니다. 이후 프로젝트에서도 “사람이 매번 같은 결정을 하고 있으면 그건 코드로 옮길 수 있다”를 먼저 봅니다.

Troubleshooting — 동시성을 풀지 않고 비껴간 결정

문제
여러 명이 같은 순간에 제출하면 집계가 어긋날 수 있다는 걸 알고 있었습니다. 퀴즈 쇼는 동점 처리와 순위가 걸려 있어서 무시할 수 없는 문제였습니다.
파고든 것
웹 서비스의 동시성 처리를 따로 공부했습니다. 락 · 큐 · 세션 관리로 제출 순서를 보장하는 방향을 검토했습니다.
멈춘 지점
제대로 하려면 서버를 띄우고 상시 운영해야 했습니다. 그런데 이 도구는 스터디 준비시간을 줄이려고 만든 것입니다. 도구를 운영하는 비용이 새로 생기면 목적이 뒤집힙니다.
해결
문제를 푸는 대신 범위를 좁혔습니다. 로컬에서 실행하고 포트만 열어 같은 네트워크(같은 IP 대역) 안에서만 동작하게 했습니다. 스터디는 어차피 한자리에 모여서 하니 요구가 충족됩니다.
감수한 것
원격 참여가 불가능합니다. 공개 서비스로 확장하려면 이 결정을 되돌리고 동시성부터 다시 풀어야 합니다.
배운 것
동시성 문제를 풀지 않고 회피했습니다. 처음엔 진 것 같았는데, 사용 맥락이 좁으면 회피가 맞는 선택일 때도 있다는 걸 알았습니다. 중요한 건 어떤 조건에서 이 결정이 깨지는지를 알고 있는 것입니다.

남은 한계

원격 참여 불가가 가장 큰 제약입니다(위 트러블슈팅 참고). 그 외에 재접속 시 상태 복원과 Notion 표 구조 변경 시 추출이 깨지는 문제가 남아 있습니다 — 남의 서비스 데이터 구조에 의존하기로 한 선택의 대가입니다.
