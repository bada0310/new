Bimp — 냉장고 식자재 인식 · 레시피 추천

2024.03 – 06 (3개월)

직접 입력의 불편을 이미지 인식으로 줄인 졸업 프로젝트. 문제를 ‘추천’이 아니라 ‘등록’으로 재정의한 데서 모든 설계가 따라 나왔습니다.

제안 · 중간 · 최종 보고서 ↗ GitHub ↗ 배포 없음 · 프로토타입

Problem · Evidence

레시피 추천을 받으려면 보유 식재료를 하나씩 직접 등록해야 했습니다. 추천에 닿기 전에 입력에서 지칩니다.

병목은 추천이 아니라 그 이전 단계였습니다. 냉장고 사진과 영수증에 이미 정보가 있으니 이를 입력 수단으로 바꿀 수 있다고 봤습니다. 기존 앱의 바코드 스캔은 포장 없는 채소·정육을 못 잡습니다.

나의 활동

4인 팀에서 YOLO 객체 인식 모델 개발 · 추천 시스템 알고리즘 · 재고 관리 로직 설계 · 프레임워크 개발을 맡았습니다. OCR API와 라즈베리파이 촬영 알고리즘은 팀 PM이, 웹 프론트·백엔드는 다른 팀원이 담당했습니다.

핵심 성과 · Key Achievements

  • 틀릴 것을 전제하고 8종만 자동화 깊이 카메라와 RFID를 각각 비용·현실성으로 기각한 뒤, 인식 범위를 8종으로 좁혀 확실한 것만 자동 처리하고 확정 전에 추가·삭제·수정을 분리한 보정 단계를 넣었습니다
  • 정확성 100% · 만족 64% 알러지 제외 정확성 22 / 22 (100%), 추천 결과 만족 14 / 22 (64%) · 불만 3명, 사용성은 ‘보통’이 12 / 22 (55%)로 과반 — 규칙으로 처리한 정확성은 완전했지만 가중치로 만든 만족도와 화면은 남은 과제라는 게 숫자로 드러났습니다
  • 병목은 추천이 아니라 등록이었다 팀이 ‘추천 정확도’를 보고 있을 때 병목은 그 이전 단계에 있다고 짚었습니다. 냉장고 사진과 영수증에 이미 정보가 들어 있으니 입력 수단 자체를 바꾸는 방향으로 스코프를 옮겼습니다
성과 1건 더 보기
  • 이종 인식 결과 통합 객체 인식(YOLOv5)과 문자 인식(OCR)을 억지로 한 모델에 합치지 않고 출력 형식만 공통 식재료 스키마로 통일 — 뒷단(추천)이 입력이 사진인지 영수증인지 몰라도 되게 만들었습니다

Technical Decision

결정한 것고른 것기각한 것사유 · 감수한 것
인식 파이프라인두 모델 병행 후 공통 스키마로 병합단일 모델로 통합 처리냉장고(객체)와 영수증(문자)은 문제 유형이 다릅니다. 억지로 한 모델에 넣는 대신 출력 형식을 통일했습니다. 감수: 중복 병합 규칙이 필요.
인식 결과 처리추가·삭제·수정 분리 + 사용자 확정 단계인식 결과 자동 확정잘못된 재고는 추천 전체를 무의미하게 만듭니다. 정확도를 올리는 대신 틀렸을 때 고칠 수 있게 했습니다. 감수: 사용자 단계가 하나 늘어남.
학습 위치Colab로컬 / EC2 GPU학습 GPU가 없었고 비용을 쓸 수 없었습니다. 감수: 세션 제한으로 학습이 끊깁니다.
재고 최신화선입선출최신순 / 수량만 관리유통기한이 앞선 것부터 소모돼야 추천이 실제 냉장고와 맞습니다.

AI 의사결정 — 정확도를 올릴 것인가, 틀릴 것을 전제할 것인가

Q. 왜 두 모델을 병행했나 — 하나로 통합하지 않고

냉장고 사진은 객체 인식 문제이고 영수증은 문자 인식 문제입니다. 입력의 성질이 다릅니다.

한 모델로 합치려면 둘 중 하나를 억지로 상대 문제로 변환해야 하는데, 그러면 둘 다 정확도가 떨어집니다. 대신 모델은 둘로 두고 출력 형식만 통일했습니다 — 공통 식재료 스키마.

얻은 것 뒷단(추천)이 입력이 사진인지 영수증인지 몰라도 됩니다. 나중에 세 번째 입력 경로가 생겨도 스키마만 맞추면 붙습니다. 치른 것 같은 품목이 두 경로로 들어오면 중복되므로 병합 규칙이 따로 필요했습니다.

Q. 인식 정확도를 왜 더 올리지 않았나 — 기각한 두 가지

겹치거나 반 개로 잘린 식재료를 세지 못했습니다. 처음엔 학습 데이터를 늘리면 된다고 봤는데 틀렸습니다. 단안 카메라에는 깊이 정보가 없어서, 가려진 뒤에 뭐가 몇 개 있는지 원리상 알 수 없었습니다.

기각한 안얻는 것왜 기각했나
3D 깊이 카메라가림 문제가 실제로 풀림학부 예산을 넘고, 냉장고 전 칸에 설치하면 비용이 배로. 한 칸만 달아도 나머지 칸은 여전히 미지
식재료마다 RFID 태그인식이 거의 완벽해짐사용자가 장 볼 때마다 태그를 붙여야 함. 원래 문제(등록이 번거롭다)를 더 키움

그래서 목표를 바꿨습니다. 정확도를 올리는 대신 인식 범위를 8종으로 좁혀 확실한 것만 자동 처리하고, 확정 전에 추가·삭제·수정을 분리한 보정 단계를 넣었습니다. 검증 범위도 냉장고 한 칸으로 한정했습니다.

배운 것 센서가 관측할 수 없는 것은 모델을 키워도 알 수 없습니다. “정확하게 만들기”와 “틀려도 되돌릴 수 있게 만들기”는 다른 목표이고, 어느 쪽인지 먼저 정했어야 했습니다.

Q. 재고 최신화를 왜 선입선출로 했나

최신순이나 수량만 관리하는 방식도 구현은 더 쉽습니다. 그런데 유통기한이 앞선 것부터 소모돼야 남은 재고가 실제 냉장고와 맞고, 그래야 추천이 의미를 가집니다.

감수한 것 사용자가 실제로 뒤쪽 것을 먼저 꺼내면 어긋납니다. 이 경우도 보정 화면에서 고칠 수 있게 두는 것으로 처리했습니다.

User Flow

확인·수정이 파이프라인의 중심입니다.

Data Flow

서로 다른 두 인식 문제를 한 모델로 합치지 않았습니다. 출력 형식만 통일해, 뒷단은 입력이 사진인지 영수증인지 모릅니다.

AS-IS → TO-BE

식재료를 손으로 하나씩 입력→촬영 한 번으로 후보 자동 추출
등록이 밀려 재고가 실제와 어긋남→구매 시점(영수증)에도 갱신
인식 결과를 그대로 확정→확인·수정을 거쳐 추천으로

Troubleshooting — 겹치거나 잘린 식재료를 인식하지 못했다

증상
냉장고 안에서 식재료가 겹쳐 있거나 반 개로 잘려 있으면 개수가 틀리게 잡혔습니다. 재고가 틀리면 추천 결과 전체가 무의미해집니다.
처음 가설
학습 데이터를 늘리면 해결된다고 봤습니다. 틀렸습니다 — 겹침·절단은 데이터 양의 문제가 아니라 단안 카메라로는 잔량 자체를 관측할 수 없는 문제였습니다.
실제 원인
Raspberry Pi 카메라 모듈 한 대로는 깊이 정보가 없습니다. 객체가 가려지면 뒤에 무엇이 몇 개 있는지 원리상 알 수 없습니다.
기각한 안
① 3D 깊이 카메라 — 깊이는 얻지만 학부 예산을 넘고, 냉장고 전 칸에 설치하면 비용이 배로 늡니다.
② 식재료마다 RFID 태그 — 인식은 정확해지지만 사용자가 장 볼 때마다 태그를 붙여야 해서 현실성이 없다고 판단했습니다.
해결
인식 정확도를 끌어올리는 대신 틀릴 것을 전제로 흐름을 바꿨습니다. 인식 범위를 8종(당근·양파·사과·달걀·양배추 등)으로 좁혀 확실한 것만 자동 처리하고, 확정 전에 추가·삭제·수정을 분리한 보정 단계를 넣었습니다. 검증 범위도 냉장고 한 칸으로 한정해 시스템이 정상 동작함을 보이는 쪽으로 정리했습니다.
배운 것
센서가 관측할 수 없는 것은 모델을 키워도 알 수 없습니다. 정확도를 목표로 잡을지, 되돌릴 수 있음을 목표로 잡을지를 먼저 정해야 했습니다.

Validation — 사용자 만족도 조사 22명

라즈베리파이를 남의 집 냉장고에 설치할 수는 없어, 추천·통계 기능에 한정해 22명에게 조사했습니다.

항목긍정보통부정읽은 것
정확성 — 알러지 식재료 제외2200규칙 기반 제외는 의도대로 동작했다
사용성 — 웹 구성7123보통이 과반. 기능은 되지만 화면은 다듬지 못했다

숫자를 보고 나서야 약점이 추천 성능이 아니라 화면이라는 게 분명해졌습니다. 조사 전에는 반대로 짐작하고 있었습니다.

한계 — 최종보고서에 남긴 것

한계무엇이 막혔나어떻게 처리했나
하드웨어냉장고 전 칸에 카메라를 달아야 하는데 비용·설치가 불가한 칸만 설치한 상황을 가정해 시스템이 성립함을 보였다
객체 인식겹침·절단 시 정확 인식 불가. 인식 가능 품목 8종가능한 범위까지만 학습하고 보정 단계로 메꿨다
정확한 양무게(g·kg) 단위 재료는 잔량 비교 불가 — 소고기 100g 보유 시 200g 레시피를 거를 수 없음깊이 카메라가 있어도 난도가 높다고 보고 범위에서 제외했다

향후 계획으로 남긴 것: 디지털 영수증 OCR · 바코드 인식(가공식품 유통기한) · 메뉴 조합 추천 · 사용자 유형별 추천.

못 한 것을 못 했다고 적은 문서입니다. 경진대회 출품이나 특허가 어렵다는 판단까지 보고서에 그대로 남겼습니다. 할 수 있는 범위를 좁게 잡고 그 안에서 끝낸 결정이, 지금도 프로젝트에 들어갈 때 가장 먼저 하는 일입니다.
